## Phase 3: 핵심 기능 개발 (3-4일)

**이유**: 핵심 기능은 Phase 2에서 만든 공통 모듈을 조립해 방문자가 실제로 사용하는 화면(PRD의 P0 요구사항)을 완성하는 단계다. 부가 기능보다 먼저 끝내야 MVP로서 의미가 있다.

**작업 항목** (PRD 5번 기능 요구사항 중 P0 항목 기준)
- 홈 페이지(`/`) 구현 — 프로필 히어로, 경력 타임라인, 프로젝트 그리드 (FR-3, PRD 8번 화면 설계)
- 프로젝트 상세 페이지(`/projects/[id]`) 구현 — 설명/역할/기술/링크, 존재하지 않거나 비공개 시 404 (FR-4)
- 이력서 PDF 다운로드 (`/api/resume/pdf`) — `@react-pdf/renderer` 템플릿 + 한글 폰트(Noto Sans KR) 등록 (FR-5, PRD "PDF 생성 및 다운로드")
- ISR 재생성 전략 적용 — 페이지/데이터 조회에 `revalidate` 설정, 방문 요청마다 Notion API 직접 호출하지 않도록 구성 (FR-9)
- 반응형 기본 대응 — 모바일에서 프로젝트 1열, 경력 세로형 (FR-8, 세부 다듬기는 Phase 5)

**완료 기준** — 🔸 Phase 3 기능 구현 완료, 검증 2건 Phase 5 로 이월 (2026-07-30)
- [x] 홈 페이지에서 노션에 입력한 프로필/경력/프로젝트가 실제로 보인다
      — 2026-07-30 확인. 프로필(나르/고양이/자기소개), 경력 3건 최신순, 프로젝트 3건
      정렬 순서 우선 + 기간 최신순 폴백까지 prerender HTML 로 검증.
- [x] 프로젝트 상세 페이지 진입/뒤로가기가 정상 동작하고, 존재하지 않는 ID는 404를 반환한다
      — 프로덕션 서버 기준 실제 ID 200, 없는 UUID 404, 형식 불량 값 404.
- [x] "이력서 PDF 다운로드" 버튼으로 한글이 깨지지 않는 PDF가 다운로드된다
      — Noto Sans KR 한국어 서브셋 TTF(400/700) 임베드. pdftotext 로 텍스트 추출해 한글 확인.
      Content-Disposition 은 RFC 5987 로 `이력서_나르.pdf`.
      **서브셋에 없는 기호(`→` 등)가 다른 글자로 조용히 치환되는 문제를 발견해
      `src/lib/pdf/sanitize.ts` 에서 폰트 characterSet 을 직접 조회해 정제하도록 했다.**
- [ ] 노션에서 값을 수정한 뒤 재생성 주기(또는 로컬 재빌드) 후 사이트에 반영된다
      — `revalidate = 3600` 적용 및 빌드 산출물에 Revalidate 1h 확인.
      실제 1시간 경과 후 반영은 미검증(로컬 재빌드 반영은 확인).
- [ ] 모바일 뷰포트(375px 기준)에서 레이아웃이 깨지지 않는다
      — 반응형 클래스는 적용했으나 실제 뷰포트 렌더는 미확인. Phase 5 QA 대상.

## Phase 4: 추가 기능 개발 — SEO 중심 (1-2일)

**이유**: 핵심 기능이 완성된 후 부가 기능을 추가해야 우선순위가 뒤바뀌지 않는다. 필터·검색을 제외하면서 실질적으로 SEO(FR-10, P0) 완성 단계가 되었다.

> **범위 확정 (2026-07-30)**: "기술 스택 필터링"과 "검색 기능"은 **범위에서 제외**한다.
> PRD의 기능 요구사항(FR) 표에 없는 제안 기능이었고, 현재 공개 프로젝트가 3건이라
> 필터·검색 UI가 오히려 방해가 되며 클라이언트 번들만 늘어 LCP KPI에 불리하다.
> **프로젝트가 10건 이상으로 늘어나면 재검토한다.**
> 이 결정으로 Phase 4는 SEO에 집중한다.

**작업 항목**
- SEO 최적화 — `generateMetadata`로 동적 title/description/OG 이미지, `sitemap.ts`, `robots.ts` (FR-10, P0이지만 개발 순서상 부가 기능 단계에 배치)
- `/api/revalidate` — 운영자용 즉시 재생성 트리거 (PRD API 설계, P1)
- ~~기술 스택(스킬) 필터링~~ → **범위 제외 확정** (위 노트 참고)
- ~~검색 기능~~ → **범위 제외 확정** (위 노트 참고)
- ~~프로젝트 정렬 순서 적용 (FR-12, P1)~~ → **Phase 2 에서 선행 완료**
- ~~Notion API 429 재시도 로직 (FR-11, P1)~~ → **Phase 2 에서 선행 완료**

**완료 기준**
- [ ] Lighthouse SEO 점수 90점 이상, `sitemap.xml`/`robots.txt`가 정상 응답된다
- [ ] 각 페이지에 `generateMetadata`로 동적 title/description/OG 이미지가 설정된다
- [ ] `/api/revalidate` 가 시크릿 검증 후 지정 경로를 재생성한다
- [x] `order` 필드가 있는 프로젝트가 지정한 순서대로, 없는 프로젝트는 최신순으로 표시된다
      — Phase 2 `fetchProjects` 의 `compareProjects` 로 구현. 노션 정렬로는 "빈 값을 뒤로"를
      표현하기 어려워 조회 후 JS 에서 정렬한다. 더미 행 검증 + 실데이터 prerender HTML 로
      순서(order 1 → order 2 → order 없음) 확인 완료.
- [~] 의도적으로 429를 유발해도 재생성 작업이 죽지 않고 재시도 후 성공한다

      어려우므로, 검증이 필요하면 SDK 의 `fetch` 옵션을 주입해 429 를 모킹하는 방식을 쓴다.

## Phase 5: 최적화 · E2E 테스트 · 배포 (2-3일)

**이유**: 기능이 완성된 후 품질을 끌어올리는 단계로, PRD의 성공 지표(KPI)를 실제로 만족하는지 마지막으로 검증한다. Phase 3에서 코드로만 확인하고 실제 브라우저 렌더를 못 본 항목들을 여기서 정리한다.

### 5-1. 성능 최적화
- ✅ **`next/image` 전환 완료 (2026-07-30, Phase 4 이전에 선행 처리)**
  - `remotePatterns` 에 `prod-files-secure.s3.us-west-2.amazonaws.com` 등록 (실측 호스트).
  - 전환 대상 3곳: `project-card.tsx`, `projects/[id]/page.tsx`,
    그리고 **`profile-hero.tsx` 의 프로필 사진**.
  - 프로필 사진은 shadcn `Avatar`(Radix) 를 걷어냈다. Radix `AvatarImage` 는 순수 `<img>` 를
    그려 최적화를 타지 않는데, 노션 프로필 사진 원본이 1MB 를 넘고 이게 홈의 LCP 이미지다.
    서버에서 이미 `avatarUrl` 유무를 알기 때문에 Radix 의 클라이언트 로드 상태 판정도 불필요했다.
  - `fill` 대신 width/height 를 쓴다. `fill` 은 position 래퍼가 필요한데 그러면 Card 의
    `has-[>img:first-child]` 선택자가 깨진다.
  - 실측: 원본 435KB → 옵티마이저 60KB(w=3840 폴백), w=128 은 2.5KB. 미허용 호스트는 400 차단.
  - **남은 리스크**: 서명 URL 유효기간이 1시간이고 페이지 `revalidate` 도 3600 이라 두 주기가
    겹친다. `next/image` 로 서버가 한 번 받아 캐시하므로 방문자마다 만료 URL 을 때리는 상황은
    없어졌지만, **캐시 미스가 만료 직후에 발생하면 여전히 실패할 수 있다.**
    필요하면 `revalidate` 를 1800 으로 낮추거나 `minimumCacheTTL` 을 조정한다(현재 기본 60초).
- 폰트 최적화(`next/font`), 불필요한 클라이언트 번들 축소 (KPI: LCP 2.5초 이내)
- 폰트 최적화(`next/font`), 불필요한 클라이언트 번들 축소 (KPI: LCP 2.5초 이내)
- 이력서 PDF 폰트 4.8MB 가 서버리스 콜드스타트에 주는 영향 측정
