# 메타 프롬프트: 노션 기반 포트폴리오 · 경력관리 사이트 MVP PRD 생성기

당신은 10년 이상 경력의 시니어 프로덕트 매니저 겸 풀스택 아키텍트입니다. 지금부터 아래 기능에 대한 **MVP PRD(제품 요구사항 문서)**를 한국어로 작성합니다.

## 1. 배경 (Context)

- 프로젝트명: career-web (Next.js 15 + React 19 기반 스타터킷 위에서 신규 개발)
- 운영자(본인)의 경력·프로젝트·자기소개를 **노션(Notion) 데이터베이스**에서 관리합니다.
- 운영자가 노션에 프로필, 경력(회사/직무/기간/성과), 프로젝트(제목/설명/기술스택/링크)를 입력하면, **누구나 로그인 없이 URL로 접속해 확인 가능한 공개 포트폴리오 웹사이트**로 노출되어야 하고, **요약 이력서를 PDF로 다운로드**할 수 있어야 합니다.
- 이 저장소는 아직 이 기능이 전혀 구현되어 있지 않은 상태이며(Notion 연동, PDF 생성, 관련 라우트 모두 없음), **완전히 새로 설계해야 합니다.**

## 2. 기술 스택 제약 (반드시 준수)

- Frontend: Next.js 15 (App Router), React 19, TypeScript (any 타입 사용 금지)
- 스타일: Tailwind CSS + shadcn/ui
- 상태관리: Zustand (필요한 경우에만)
- 폼: React Hook Form + Zod (필요한 경우에만 — 이 기능은 방문자 입력을 거의 받지 않음)
- 백엔드/DB: 기본적으로 Supabase 없이 Next.js ISR(`revalidate`)만으로 캐싱한다. 트래픽/실시간성 요구가 커질 경우에만 Supabase 캐싱을 P2로 검토한다 (공개 개인 사이트는 견적서처럼 요청마다 실시간 조회할 필요가 없으므로 과설계를 피한다).
- 외부 연동: Notion API (`@notionhq/client` 등, 공식 SDK 기준으로 설계)
- 반응형 UI 필수 (모바일에서도 포트폴리오 확인 가능해야 함)
- SEO 필수 (완전 공개 사이트이므로 검색엔진 노출이 핵심 목표 중 하나)
- 로그인/인증, 결제, 방문자 문의 폼 백엔드(이메일 발송 등)는 **MVP 범위 밖** — Out of Scope 섹션에 명시만 하고 상세 설계는 하지 않는다.

## 3. MVP 핵심 플로우

1. 운영자가 노션 DB(프로필/경력/프로젝트)에 콘텐츠를 입력/수정한다 (Source of Truth = Notion).
2. Next.js가 재생성 주기(ISR `revalidate`)마다 Notion API로 최신 데이터를 조회해 정적 페이지를 갱신한다.
3. 방문자가 사이트 URL(검색엔진 또는 공유 링크)로 접속하면, 캐시된 정적 페이지가 즉시 응답된다 — 방문 시점에 Notion API를 직접 호출하지 않는다.
4. 방문자는 "이력서 PDF 다운로드" 버튼을 눌러 프로필+경력 요약을 PDF로 받는다.

## 4. PRD에 반드시 포함해야 할 섹션 (아래 순서와 제목 그대로 사용)

1. **개요 (Overview)** — 한 문단 요약
2. **문제 정의 및 목표** — 현재 문제, 이 기능으로 해결하려는 것, 성공 지표(KPI) 2~3개 (예: LCP, PDF 다운로드 성공률, 반영 지연 시간)
3. **사용자 및 시나리오** — 운영자(내부 사용자) / 방문자(외부 사용자, 채용 담당자 등) 페르소나와 각각의 유저 스토리(As a ~, I want ~, So that ~ 형식)
4. **핵심 유저 플로우** — 위 3번 플로우를 단계별 다이어그램(mermaid `flowchart` 또는 `sequenceDiagram`)으로 표현
5. **기능 요구사항 (Functional Requirements)** — 표 형식(ID, 요구사항, 우선순위(P0/P1/P2), 비고)으로 정리. 최소한 아래 항목 포함:
   - 노션 DB(프로필/경력/프로젝트) 스키마 정의 및 필드 매핑 규칙
   - 노션 데이터 조회 및 ISR 재생성 전략 (요청 단위 실시간 호출 지양)
   - 홈 페이지 및 프로젝트 상세 페이지 UI
   - 공개여부(draft/published) 필터링 — 비공개 콘텐츠는 노출 금지
   - 이력서 PDF 생성 및 다운로드 (라이브러리 후보 2~3개를 장단점과 함께 비교 — 예: `@react-pdf/renderer`, `puppeteer`+HTML, `jspdf` — 서버리스 배포 가능성을 고려해 적합한 것을 추천하고 이유 명시)
   - SEO(메타태그, sitemap, robots.txt)
   - 노션 필드 누락/타입 불일치에 대한 방어적 처리
6. **비기능 요구사항 (Non-Functional Requirements)** — 성능(LCP 등 Core Web Vitals), 보안(공개 사이트이지만 비공개 콘텐츠 노출 방지, Notion API 키 노출 방지), 반응형, SEO, 에러 핸들링 원칙, API 응답 형식 일관성
7. **데이터 모델** — 노션 DB(프로필/경력/프로젝트) 필드 스키마(표), 노션 필드 ↔ 내부 타입 매핑 예시 TypeScript interface
8. **화면 설계** — 홈 페이지(프로필+경력 타임라인+프로젝트 목록)와 프로젝트 상세 페이지의 주요 구성요소를 텍스트로 와이어프레임 설명, shadcn/ui 컴포넌트 중 재사용 가능한 것 명시(`card`, `badge`, `avatar` 등)
9. **API 설계** — 라우트 목록(표: Method, Path, 설명, 요청/응답 형식), 기존 `ApiResponse<T>` 공통 타입 컨벤션 준수. 목록 조회는 별도 공개 API 없이 Server Component에서 직접 처리해도 됨을 고려
10. **Out of Scope (MVP 제외 범위)** — 로그인/인증, 방문자 문의 폼 백엔드, 관리자 웹 편집 UI, 방문 통계/분석 대시보드, 다국어, 블로그 등 명시적으로 제외
11. **리스크 및 오픈 이슈** — 노션 스키마 변경 시 깨짐 가능성, PDF 렌더링 시 한글 폰트 깨짐 이슈, ISR 반영 지연, 노션 이미지 URL 만료 이슈 등
12. **마일스톤 (초안)** — 단계별 개발 순서 제안 (예: 1) Notion 연동 및 데이터 조회 → 2) 홈/상세 UI → 3) SEO → 4) 이력서 PDF → 5) QA)
13. **사전 준비 사항 (Notion 연동 체크리스트)** — Notion Integration 생성 및 API 키 발급, 대상 DB에 Integration 연결(Add connections), DB ID 확인, 필드 스키마 일치 확인, 환경변수 전달 등 사용자가 직접 준비해야 할 항목을 체크리스트로 정리

문서 마지막에는 "확인 필요 사항" 목록을 별도로 정리한다 (예: 프로필을 DB로 관리할지 단일 페이지로 관리할지, 프로젝트 정렬 방식, revalidate 주기, 이력서 PDF 포함 항목, 커스텀 도메인 여부 등).

## 5. 출력 형식 지침

- 전체 문서는 **한국어**로 작성 (기술 용어/코드 식별자는 영어 유지)
- 마크다운 문서 하나로 작성, 위 13개 섹션을 `##` 헤더로 구분
- 표가 필요한 곳(기능 요구사항, API 설계, 데이터 모델)은 반드시 마크다운 표 사용
- 유저 플로우는 mermaid 코드 블록 사용
- 각 기능 요구사항에는 우선순위(P0=MVP 필수, P1=있으면 좋음, P2=향후)를 명시
- 불확실하거나 사용자 확인이 필요한 지점은 문서 마지막에 "확인 필요 사항" 목록으로 별도 정리
